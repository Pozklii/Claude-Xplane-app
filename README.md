# Flight World

A web app for logging and reviewing flights, built with Next.js, Supabase, and deployed on Vercel.

## Stack

- [Next.js](https://nextjs.org) (App Router, TypeScript, Tailwind CSS)
- [Supabase](https://supabase.com) for auth and data storage
- [Vercel](https://vercel.com) for hosting, deployed from this GitHub repo

## Getting started

1. Install dependencies:

   ```bash
   npm install
   ```

2. Create a Supabase project at [supabase.com](https://supabase.com), then copy `.env.local.example` to `.env.local` and fill in your project's URL and anon key (Project Settings → API):

   ```bash
   cp .env.local.example .env.local
   ```

3. Create the `flights` and `user_preferences` tables and their row-level security policies by running [`supabase/schema.sql`](./supabase/schema.sql) in your project's SQL editor (Supabase dashboard → SQL Editor → New query). **Already set up from an earlier version?** Run [`supabase/migrations/20260926_ratings_and_favourites.sql`](./supabase/migrations/20260926_ratings_and_favourites.sql) instead — it adds the `flights.rating` column and the `user_preferences` table, and is safe to run more than once. Do this before deploying the ratings/favourites code, since the flights page selects the new column.

4. In the Supabase dashboard, under Authentication → URL Configuration, set the **Site URL** to `http://localhost:3000` for local development (and add your Vercel domain once deployed). Email/password sign-up is enabled by default and requires confirming a link sent by email before a user can sign in.

5. Run the dev server:

   ```bash
   npm run dev
   ```

   Open [http://localhost:3000](http://localhost:3000).

## Deploying

Import this repository in [Vercel](https://vercel.com/new), add the same two environment variables from `.env.local` in the project's settings, and deploy. Every push to `main` will trigger a new deployment.

After deploying, add your Vercel URL (and any preview URLs) to Supabase's Authentication → URL Configuration → Redirect URLs so email confirmation links work in production.

Free-tier Supabase projects are paused after a period of inactivity. While paused, the auth API is unreachable and sign-in/sign-up fail with a "can't reach the sign-in service" message — restore the project from the Supabase dashboard (it takes a few minutes to come back up).

## Features

- A landing page (`/`) with a moving fractal-flame background, one of three picked at random on each visit (rose and blue veils, orange and blue embers, or a blue and teal vortex): rendered live in WebGL2 (`flame-gl.ts`: the same chaos game the stills in `public/sky/flame-*.webp` were drawn with, run on the GPU each frame with every transform slowly swaying, so the shapes curl and morph; parameters in `flame-params.ts`), under a pulsing glow layer and twinkling motes orbiting the middle (`flame-motes.tsx`). `?sharp=1` previews crisper versions (sharper stills, the live flame at full resolution without blur, no glow layer). The still shows first and stays wherever the live flame can't run (no WebGL2, a device too slow for it, or `prefers-reduced-motion`, which also stills everything else). `?bg=veil`, `?bg=ember` or `?bg=vortex` picks one, and `?bg=golden` shows the earlier golden-hour sky — a low sun just off the top-left corner, sun-lit cumulus and slowly breathing light shafts — and an animated gold wireframe turbofan that draws itself in, ring by ring from the intake back, grows its fan, spools up and flies nearly level, facing right, with its exhaust streaming off to the left (canvas 2D, `engine-fx.ts`; shown as a still under `prefers-reduced-motion`). The engine is the hero's centrepiece, in the middle of the first screen, with the heading and the example-flight card to its left and the globe to its right (stacked on phones). Under the heading are **Flight Log**, **Flight Map** and **Flight Plan** buttons (`app-links.tsx`): greyed out behind a lock with a "Sign in to use these" hint for visitors, working links once signed in (when the Sign in button also goes). The same three links replace the header's single Flights link when signed in. Each is its own page: the Flight Map (`/flights`) has the globe (or 2D map) and the selected flight's summary card, and nothing else; the Flight Log (`/log`) has logging a new flight, your favourites and flying summary, and the list of flights, with the picked flight's summary card at the top (choosing one scrolls up to it) and a "Show on Flight Map" link that opens it there (`/flights?flight=<id>`); Flight Plan is `/plan`, which opens with a From and To route: the great-circle distance between two airports (nm, km and miles), the initial heading and a rough flight time (`route-planner.tsx`). To the engine's right is a live example globe (add `?map=2d` to the landing or flights page URL to preview it as a flat 2D map instead) using the same `FlightGlobe` component as the flights page. The globe tours an endless stream of generated example flights: every 7 seconds it generates a new one and flies onto it, keeping the last six drawn. They're built from a table of real airlines on routes they're known for, with aircraft types they typically fly there, plus a few private/GA hops (`src/lib/example-flights/routes.ts`); the generator (`src/lib/example-flights/generate.ts`) randomizes direction, aircraft, date (anywhere from the visitor's own today back ~18 months — dated in their browser, since the page itself is prerendered) and notes (two sentences from different phases of flight, drawn from a pool of templates in `notes.ts` that avoids phrasings already on screen and airline-only details on private flights), and estimates flight time from the real great-circle distance and the aircraft's cruise speed. Airport coordinates come from the bundled OurAirports lookup, and routes crossing the antimeridian are skipped. A summary card (the same one as the flights page, minus thumbnail and close) shows its route, distance, flight time, date, aircraft, airline and notes. The tour can be paused. The globe is always shown whole, never zoomed or tilted in past its own edges: it just turns to face each flight. The landing globe is display-only (`FlightGlobe`'s `interactive={false}`: MapLibre's handlers off and `pointer-events: none`), so it can't be dragged, zoomed or clicked, and scrolling over it scrolls the page; the tour alone drives it. The flights page's globe stays fully interactive, and is shown whole the same way: selecting a flight turns the globe to face it rather than zooming and tilting in, and its round frame only appears once you zoom in yourself (or fly into an airport). On a PC everything, the feature blurbs included (in a compact row under the engine and globe), fits in one screenful with no scrolling; the engine shrinks on shorter screens to make room. It all sits on one continuous sky. The sky is pre-rendered into two images in `public/sky/` (the sky itself, and the light shafts, screen-blended on top) rather than generated in the browser, which would cost a noticeable pause on slower devices; on portrait screens it's shown across the top at close to its designed scale and fades into a matching base colour, rather than zooming into the sun. It's a deliberately single theme rather than adapting to light/dark preference.
- Email/password sign-up and sign-in via Supabase Auth (`/login`)
- Protected Flight Log (`/log`) and Flight Map (`/flights`) pages for logging and reviewing your flights (date, airline, aircraft, route, hours, notes), backed by a `flights` table scoped to each user via row-level security
- A rotatable, self-rotating 3D globe on the flights page — the same frameless, circular globe as the landing page, on the same dark ground (bare mode leaves the land transparent so that ground shows through) — rendered with [MapLibre GL JS](https://maplibre.org/maplibre-gl-js/docs/) over free, no-API-key [OpenStreetMap](https://www.openstreetmap.org/copyright) vector tiles from [OpenFreeMap](https://openfreemap.org/) (swap `STYLE_URL` in `flight-globe.tsx` for a MapTiler/Mapbox satellite style if you have a key). Idle at the overview zoom, it spins slowly on its own (nudging the center longitude every frame, not the bearing, so it reads as the Earth turning rather than the camera orbiting) — paused for the duration of any drag/rotate/pitch gesture or programmatic camera move, and skipped entirely under `prefers-reduced-motion`. Flight routes are drawn with [deck.gl](https://deck.gl/)'s `ArcLayer`, composited into the MapLibre render pass via `@deck.gl/mapbox`'s `MapboxOverlay` (`interleaved: true`), styled as glowing arcs in one flat color end to end (a wide, low-opacity layer under a thin, bright one approximates the glow, since deck.gl has no native bloom) — airports have no visible marker (a flat disc on the globe's surface z-fights with it and flickers), but a fully transparent `ScatterplotLayer` keeps them clickable, since deck.gl picks by its own picking colors rather than fill alpha. The selected route is drawn as its own pair of layers with constant colors/widths rather than per-arc accessor functions — deck.gl only re-runs accessor functions when the data or an `updateTriggers` entry changes, so a function would keep drawing the old color/selection. Clicking a route highlights it on the globe (with its two airports' city/code labels), highlights the matching entry in the flight log below, and vice versa, and flies the camera in on the two airports with a 55° pitch; deselecting eases back out to the full overview. Clicking an individual airport marker flies in further still (zoom 15, 60° pitch) — close enough for MapLibre's native 3D buildings to render, showing that airport's actual OpenStreetMap building footprints in 3D rather than a generic marker. Airport coordinates come from a bundled ICAO/IATA lookup, derived from [OurAirports](https://ourairports.com/data/) (public domain) — no coordinates to enter manually. On the flights page, a color swatch above the globe lets you pick the color used for every route in place of the default cyan, applied immediately without moving the camera. Selecting a flight (on the globe or in the log) pulses its route's glow while the camera flies in, and animates a details card into the globe band: a thumbnail, the route's city names, great-circle distance (haversine, in nm and km), logged flight time, date, aircraft, airline and the flight's notes — the numbers count up from zero. An always-visible **Add/Change thumbnail** button on the card opens a picker to choose one of the flight's uploaded images or upload a new one; the choice is stored as its own copy at `{user id}/thumbnails/{flight id}/…` in the `flight-media` bucket (already covered by its per-user storage policies, so no schema change), replacing the previous one. Without a chosen thumbnail the card falls back to the flight's first uploaded image, then to a drawn route graphic. All of it is skipped under `prefers-reduced-motion` — remembered in `localStorage`, so it's per-browser rather than synced to your account.
  - The globe's basemap is stripped down to just airports on load: every style layer is hidden (`setLayoutProperty(id, "visibility", "none")`) except water (so it still reads as a globe), the widened `fill-extrusion` buildings above, and anything on the OpenMapTiles `aeroway` / `aerodrome_label` source-layers — an airport's physical layout (runways, taxiways, aprons/stands) and name label. Everything else (place/road/POI labels, landcover/landuse texture, roads, boundaries, hillshading) is otherwise just clutter at globe scale.
  - **Pinned to `maplibre-gl@5`, not the current v6** — v6 changed how it bundles its background Web Worker (used to process map data off the main thread), and that pattern doesn't get picked up correctly by Next.js's Turbopack: no worker is ever created, so every GeoJSON layer (the flight routes and airport markers) silently renders nothing, with no error. v5 doesn't hit this. Worth re-testing after a Turbopack or MapLibre update in case it's since been fixed upstream, but don't bump the major version without confirming flights actually render on the globe first.
  - deck.gl's `ArcLayer` needs `parameters: { cullMode: "none" }` under the globe projection — `GlobeView` back-face-culls by default, which otherwise hides most of an arc's tube geometry depending on viewing angle.
  - Click-to-select is driven by MapLibre's own `click` event calling `overlay.pickObject()` directly, rather than a layer's own `onClick` prop — in `interleaved: true` mode, MapLibre owns input handling and only forwards a subset of events to deck.gl, so a layer's `onClick` doesn't reliably fire from real clicks even though picking itself works.
  - The fly-to camera uses MapLibre's `cameraForBounds()` to fit the two selected airports (falling back to a simple midpoint if it returns nothing, e.g. for antipodal-ish points), rather than hand-computing zoom from the coordinate spread.
  - The style's `fill-extrusion` building layer(s) have their zoom range explicitly widened on load (`map.setLayerZoomRange(id, 0, 24)`) so they're not gated behind whatever minzoom the upstream style tuned for street-level browsing — the actual level of detail still depends on how well OpenStreetMap has mapped that specific airport's buildings; some are well-mapped with individual terminal footprints and heights, others may show little more than the runway/tarmac outline.
- Screenshots/videos per flight, uploaded to a private Supabase Storage bucket (`flight-media`) scoped to each user
- **Flight ratings** — rate each flight out of 10, when logging it or at any time afterwards from the log, including flights logged before ratings existed (click a segment to set or change it; click the current one again to clear). Shown on the details card, with your average in the page header.
- **Country flags and airline logos** — each flight's departure/arrival country flag (SVGs from [flag-icons](https://github.com/lipis/flag-icons), MIT) and its airline's logo. Airline names are matched to IATA codes (by code, normalized name, or a small table of brand names like KLM/SAS/LATAM that differ from the dataset — `src/lib/airlines.ts`), and logos load from public CDNs keyed by that code (pics.avs.io, then images.kiwi.com), falling back to a monogram. Ambiguous names get the monogram rather than a guessed logo. On the flights page, the selected flight's card is the focus: wider, with a glow in its route colour, and headed by the airline with its logo shown large; a flight without a photo gets a block in its route colour. Choosing a flight from the log scrolls its card into view, and the other routes fade back so the selected one stands out. The flights can be shown on the globe or a flat 2D map with straight route lines (remembered per browser), in one of seven route colours.
- **Your flying** — favourite airline and aircraft (saved per user in `user_preferences`), the airlines you fly with (logos and flight counts, favourite starred) and the countries your flights have touched.
- **Flight Plan** — a page of its own (`/plan`, signed in only), personalised from your log (most-used airports as quick picks, your favourite or most-flown aircraft, routes you've already flown), with three tabs:
  - **Airports** — look up any airport by ICAO/IATA code, click one on the flights page's globe (it still flies in to the 3D buildings, and a button under the globe opens it here, via `/plan?airport=CODE`), or pick one of your most-used airports: its name, codes, and a note if it's a famously challenging airport. Its live METAR is opt-in — **Show live METAR** reveals it (and only then fetches it), staying on for other airports until hidden — decoded into flight category, wind, visibility, cloud, weather, temperature, QNH and the best-aligned runway's headwind/crosswind. METARs come from NOAA's [Aviation Weather Center](https://aviationweather.gov/data/api/) via `/api/metar` (cached 5 minutes) and are decoded by `src/lib/metar.ts` from the raw report text.
  - **Real-world routes** — type an aircraft (model or ICAO designator: `A20N`, `B738`, `Zibo 737-800`, `Q400`…) to see real routes airlines fly with it, from the route table in `src/lib/example-flights/routes.ts` (also used by the landing page tour), with distance, estimated block time, and badges for your favourite airline, challenging airports and routes you've already flown. Defaults to your favourite (or most-flown) aircraft.
  - **Challenging flights** — "challenging right now": airports whose current METAR makes for a demanding arrival (gusts, crosswind on the best runway, low IFR, thunderstorms, freezing precipitation), scored by `/api/weather-challenges` over the curated airports plus a watchlist of big hubs; and a curated list of famously challenging approaches (Lukla, Paro, Saba, Courchevel, St Barths, Madeira, Gibraltar, Queenstown…) with why, difficulty, elevation and runway length, and a real route in to try. The live list is only fetched once the tab is opened.

### Reference data

Bundled in `src/lib/data/`, generated by the scripts in `scripts/`:

- `airports.json` / `airport-details.json` — [OurAirports](https://ourairports.com/data/) (public domain). `scripts/augment-airport-data.mjs` adds each airport's country and OurAirports ident to the existing lookup (without changing its keys, names or coordinates, so logged flights keep resolving) and writes elevation, type, codes, Wikipedia link and runways to `airport-details.json`. Re-run it with a fresh `airports.csv`/`runways.csv` download to update.
- `airlines.json` — airline names and IATA/ICAO codes from [OpenFlights](https://openflights.org/data) (Open Database License), built by `scripts/build-airline-data.mjs`.
- Country names and details come from the [countries-list](https://github.com/annexare/Countries) package (MIT).
